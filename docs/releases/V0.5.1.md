# V0.5.1 发布说明

发布日期：2026-09-07

## 发布定位

v0.5.1 只加固在线连续规划控制平面的安全契约与状态机，不修改 grasp、IK、
depalletizing、conveyor、base optimization、碰撞检测或时间参数化算法，也不优化
或重新声明真实 M-710iD/70 规划成功率。

## 安全契约变化

- 新增不可变 `RobotStateRevision` 和 `PlanningWorldSnapshot`。快照包含 scene
  revision、实际 scene、`current_q`、robot/tool/payload、base、conveyor 和配置身份。
- `PlanningRequest` 必须绑定完整 world snapshot，request id 在 session 生命周期内唯一。
- `PlanEnvelope` 记录 expected start/end、predecessor plan id 和 planning generation。
- 执行前检查轨迹 DOF、有限性、实际 `current_q` 连续性和完整 planning context。
- backend 返回类型、target/candidate 身份或轨迹契约错误均 fail closed 到 `RECOVERY`。
- backend planning/validation 异常 fail closed；显式 `TIMEOUT` 会完成失败路径，不会死锁。

## 状态迁移变化

- `EXECUTING + new scene -> STOPPING`，不再立即从执行前关节状态重规划。
- `STOPPING + stop acknowledgement(latest scene, real stopped_q) -> PLANNING`。
- stop acknowledgement 前不启动 replan；ack 后以真实 `stopped_q` 创建新请求。
- scene revision 变化推进 generation，旧 pending/in-flight 结果到达时直接丢弃。
- `EXECUTING + success + no new scene -> WAITING_FOR_SCENE`。
- speculative k+1 的起点必须等于 plan k 的预测终点。
- 单个 request 失败不再把仍有 READY/EXECUTING/PLANNING/pending 的 session 置为
  `BLOCKED`；只有全部工作耗尽后才进入全局 `BLOCKED`。
- scene 和 robot revision 在 update、completion、stop acknowledgement 等入口统一执行
  单调性检查；相同 sequence 不允许对应不同 fingerprint。

## 新增回归测试

- 错误轨迹起点和错误 DOF/候选身份不能进入 READY/执行。
- `current_q` drift 触发失效并从真实关节状态重规划。
- planning 期间 scene 变化会丢弃旧 generation 的晚到结果。
- execution 期间 scene 变化在 stop ack 前不重规划，ack 后使用真实 `stopped_q`。
- 执行成功但没有新 scene 时等待 perception 更新。
- 所有 world/revision 入口拒绝相同 sequence、不同 fingerprint。
- 多 request 中一个失败、另一个成功时不会错误进入 `BLOCKED`。
- backend 错误类型、validation 异常和 timeout 都有终止状态。
- speculative start/predecessor 契约和全候选失败的明确 `BLOCKED`。
- world snapshot 会递归脱离调用方的可变输入。

## 仍未解决的问题

- 本版本的 async executor 是确定性的协作式抽象，不负责强制中断正在底层执行的阻塞
  planner；生产 backend 仍需提供可取消调用和硬 deadline。
- STOPPING 只定义控制平面握手，不包含真实机器人控制器的停止命令、制动确认或安全 PLC。
- perception/robot/controller 到 `PlanningWorldSnapshot` 的生产适配器尚未接入真实设备。
- V3 原始任务仍为完整几何 0/104、连续场景 0/129；底层成功率不属于本修复范围。
- 当前 CPU stop-to-stop 时间模型不代表生产节拍，`production_throughput` 继续为 `null`。

## Provider-neutral backend contract addendum

The hardening branch now also records backend identity/provenance and declared
capabilities, separates domain failures from operational outcomes, requires an
independent authoritative `PlanValidator` before `READY`, and supports
capability-driven fallback across semantic FAST/WARM/COLD routes. Backend
initialize/prewarm timing is separated from queue, compute, validation, and
end-to-end request latency.

The added regression profiles are fake semantic backends only. No external
planner, accelerator runtime, robot geometry, or concrete adapter was added.
`production_throughput` remains `null`.
