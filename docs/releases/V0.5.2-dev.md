# V0.5.2 开发说明

当前包版本为 `0.5.2.dev4`。这是在线连续规划控制平面的开发版本，不是生产节拍、
真实机器人连续执行或 M-710iD/70 完整车厢卸货能力声明。

## dev4 scope

- A bounded thread-safe MPSC `RuntimeIngressMailbox` accepts immutable planning
  requests and authoritative observations from external threads. The
  `step()` owner remains the sole state-machine writer; mailbox shutdown is
  idempotent and later submissions return `REJECTED`.
- `RuntimeWatchdogPolicy` uses an injected local monotonic clock for scene
  freshness, feedback silence, stop acknowledgement, stopped-observation,
  planning timeout, and backend-health gates. Deadlines are configurable or
  disabled with `None`; no wall clock or fixed test sleep is used.
- Feedback silence follows the real STOPPING path and sends one stop command.
  Stop/observation deadlines never fabricate a stopped state. Planning timeout
  requests cooperative cancellation and discards a late completion by
  generation; Python worker threads are not forcibly terminated.
- Runtime/session event journals and long-term samples/tombstones are bounded.
  `events_since` reports oldest/latest sequence, overflow and history gaps so a
  lagging audit consumer cannot mistake truncated history for complete history.
- New explicit reasons include `SCENE_STALE`, `PLANNING_TIMEOUT`,
  `EXECUTION_FEEDBACK_TIMEOUT`, `STOP_ACK_TIMEOUT`,
  `STOP_OBSERVATION_TIMEOUT`, and `BACKEND_UNHEALTHY`.
- This release adds no ROS, controller, planner-provider, GPU, grasp, IK,
  collision, conveyor, depalletizing, base-optimization, or time-parameterizing
  implementation. Metrics remain planning/control-plane diagnostics and
  `production_throughput` remains `null`.

## dev3 范围

- 新增不可变 provider-neutral `WorldObservation`，以 AUTHORITATIVE/PREDICTED 明确安全
  权限。producer、stream、epoch、sequence 建立观测序列域；source 只用于诊断。
- 相同观测幂等、旧观测标记 stale、相同身份不同内容 fail closed；producer epoch 更新后
  sequence 可以从零重新开始。只有 AUTHORITATIVE 能更新真实 session world。
- execution feedback 按 feedback stream、producer epoch 和 execution ID 分域。每次执行
  可以重新从 sequence 0 开始；旧 execution 的迟到反馈不能推进新 execution。
- 显式校验 ACCEPTED/RUNNING/STOPPING/terminal 状态迁移和 command acknowledgement
  capability。RUNNING 后 ACCEPTED、STOPPING 后 RUNNING、terminal 后冲突结果均拒绝。
- STOPPED feedback 与 authoritative world observation 可以任意顺序到达。缺少匹配 world
  时进入 `WAITING_FOR_OBSERVATION`，保留实际 STOP boundary，禁止 successor 与 replan，
  待 q/DOF/revision 兼容后才调用 session stop acknowledgement。
- initial request、world observation 和 execution feedback ingress 均有独立容量和每 step
  处理上限；同 stream observation 可安全合并，terminal feedback 不因压力静默丢弃。
- runtime 不再直接写 `session.state`，统一使用 session 的公开 fail-closed recovery 入口，
  由 session 维护 lineage、pending work、事件和原因。
- 新增 accepted/stale/duplicate/conflict/coalesced/backpressured/rejected、stale feedback 和
  stop observation waiting 指标。它们仍是控制面审计数据，不是物理节拍。

## dev2 范围

- 新增 provider-neutral `ExecutionBackend`，独立声明 identity、execution capabilities、
  health/state、start、poll、request_stop、current_boundary 和 shutdown 契约；不复用
  planner capabilities，也不按后端名称分支。
- 不可变 `ExecutionFeedback` 区分 ACCEPTED、RUNNING、STOPPING、STOPPED、SUCCEEDED、
  FAILED、REJECTED、DEVIATED 和 FAULTED。runtime 校验 sequence、progress、执行身份、
  DOF、有限性和完整 boundary；完全相同的 terminal 重复可幂等忽略，冲突 terminal、
  倒序或错误身份一律 fail closed。
- completion 与 stop acknowledgement 贯穿实际完整 `MotionBoundaryState`。expected end
  不得冒充 actual feedback；实际 q/qd/qdd/time/mode 偏差会使 successor 级联失效。
- `DeterministicSimExecutionBackend` 无线程、无 sleep，由调用方 `advance`，仅为控制平面
  状态机 fixture。确定性插值不表示动力学、控制器、轨迹跟踪或真实机器人周期。
- `SuccessorRequestFactory` 只生成下一步 planning request；runtime 对同一个 executing
  plan 最多提交一个 live successor，并继续经过 session 的 revision、boundary、lineage、
  generation、validation 和 rolling-horizon 门控。
- `ContinuousPlanningRuntime` 在调用 `step` 的线程中按固定顺序处理 execution feedback、
  world observation、planning completion、execution start、successor、stop request、
  deterministic advance 和状态/审计同步。planning worker 和 execution backend 都不能直接
  修改 runtime/session。
- execution feedback 与 world observation 是独立事实源。成功反馈不生成 scene；没有新的
  world observation 时保持 `WAITING_FOR_SCENE`。执行中 scene 更新进入 `STOPPING`，收到
  实际 STOP boundary 和最新 world 前不得重规划。
- 增加纯控制面 execution/runtime 计数；planning latency 口径不变，
  `production_throughput` 继续为 `null`。

## dev1 范围

- `CooperativePlanningExecutor` 明确表示旧的合作式 FIFO 语义：`submit` 只入队，
  `advance` 才在调用线程执行。`DeterministicAsyncPlanningExecutor` 仅为弃用兼容名，
  不创建后台线程。
- `SynchronousPlanningExecutor` 保持 `submit` 立即在调用线程计算的兼容语义。
- `ThreadedPlanningExecutor` 使用一个标准库 worker thread 严格按 FIFO 启动任务。
  worker 只产生不可变 completion；只有 session 调用 `advance`/poll 时才能改变状态、
  READY 队列、事件、generation、lineage 和统计。
- queued task 可在开始前真实取消且不会调用 backend。running task 只能发起合作式
  logical cancellation，不能强杀 Python thread；不支持 logical cancel 的 backend 会产生
  明确事件，晚到结果仍由 generation/lineage 门控丢弃。
- `shutdown` 幂等，关闭后拒绝 submit，可取消 pending task。`wait=False` 不代表 running
  worker 已停止；`wait=True` 使用有限 timeout，并要求调用方确保 backend 能退出。
- latency 分离为 queue、executor compute、backend-reported、authoritative validation 和
  end-to-end。executor 实测 compute 是控制面权威值；backend 自报值仅作诊断，不得覆盖。
  initialize/prewarm 继续独立统计，并增加 cancellation 与 stale-result 计数。
- 确定性并发测试使用 `threading.Event` 和有限 timeout，不以固定 sleep 推断调度状态；
  每个测试显式 shutdown worker。

## dev0 范围

- `MotionBoundaryState` 明确保存 `q`、`qd`、`qdd`、时间和
  `STOP_BOUNDARY` / `CONTINUOUS_BOUNDARY`。匹配使用显式 tolerance，并比较完整
  边界；相同 `q`、不同 `qd` 不可复用。
- `PlanEnvelope` 保存完整 expected start/end boundary，同时保留只读的旧 position
  属性。`PlanArtifactKind` 区分 geometric path 与 time-parameterized trajectory。
- geometric path 只能表达 stop boundary。当前几何 backend 仍为 stop-to-stop，本轮
  未增加时间参数化算法。
- plan lineage 记录成功完成集合、最后成功 plan 及 parent-to-child 关系。successor
  只有在准确 predecessor 成功后才能执行；failure、deviation、STOPPING 和
  invalidation 会级联失效 descendant。
- rolling horizon 计入 executing、ready、speculative、active planning 和 queued
  planning plan slots；同一 active/submitted request 不重复计数。horizon 2 表示 k 加
  最多一个 k+1，同一 predecessor 最多一个 live successor。
- backend capability、provenance、domain/operational failure taxonomy 保持 provider
  neutral。unsupported route 不计为 IK、collision 或物理不可行。
- backend `SUCCESS` 仅为 proposal。独立 `PlanValidator` 接口验证最新 snapshot、完整
  boundary、lineage 和模型 fingerprint 后才可进入 `READY`。兼容 adapter 可以代理
  v0.5.1 backend validation hook，但不能绕过 provider-neutral 门控。
- candidate/request/result/event 的嵌套 metadata 递归冻结，调用者后续修改原始
  dict、list 或 ndarray 不会改变控制平面记录。

## 明确不包含

- 不实现真实机器人 execution adapter、ROS/视觉输入输出、controller trajectory streaming、
  无缝 blending 或安全 PLC；这些留给 dev3 端口和后续 integration 工作。
- 不实现或导入 VAMP、cuRobo、CoAd、CUDA、ROS 2 或新的仿真依赖。VAMP/cuRobo
  将来只能作为 `PlannerBackend` / `PlanValidator` adapter；CoAd 类方法只能作为必须
  重新验证的 FAST proposal source。
- FK、IK、机器人/环境碰撞几何、轨迹优化、时间参数化、grasp、depalletizing、
  conveyor 和 base optimization 继续归 feasibility/integration 功能线，本轮没有从
  `feat/v0.5-feasibility-core` 合并、cherry-pick 或复制实现。

## 验收边界

V3 原始 M-710iD/70 基线仍为完整几何 0/104、连续场景 0/129。测试不依赖这些任务
成功；bottom-alternative fixture 仍是当前唯一真实 M-710iD/70 integration witness。
rolling horizon 不等于无停顿连续运动。本版本不声明真实卸货成功率或
900 boxes/h，`production_throughput` 保持 `null`。

测试继续使用 synthetic scenes、deterministic unit scenes 及既有 bottom-alternative
fixture，不依赖第三方库、硬件或固定 sleep。

dev1 的 threaded fixture 使用真实后台 worker，但不连接硬件或第三方 planner。Python
thread 不保证纯 Python CPU planner 并行，不提供 hard deadline，也不能安全强杀 running
planner。dev2 的 deterministic execution fixture 也不连接真实 controller。本版本只证明
执行 k 时控制面可自动安排 k+1、处理实际 boundary 和安全停止握手，不证明 k/k+1 已实现
非零速度无缝拼接，更不代表真实卸货吞吐。

VAMP/cuRobo/CoAd 仍只是未来 adapter：前两者只能经 provider-neutral
`PlannerBackend`/`PlanValidator` 接入，CoAd 类方法只能提供必须重新验证的 FAST proposal。
本版本未安装、导入或实现这些适配器。

dev3 仅定义未来 ROS/perception adapter 可以实现的中立事件端口，没有实现 ROS 消息、视觉
算法或真实 controller adapter。后续 execution adapter 负责控制器命令与反馈，perception
adapter 负责独立 authoritative world observation；两者都不得绕过 session 的 validation、
revision、boundary 或 lineage 门控。
