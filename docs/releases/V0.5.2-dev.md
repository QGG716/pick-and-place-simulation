# V0.5.2 开发说明

当前包版本为 `0.5.2.dev1`。这是在线连续规划控制平面的开发版本，不是生产节拍、
真实机器人连续执行或 M-710iD/70 完整车厢卸货能力声明。

## dev1 范围

- `CooperativePlanningExecutor` 明确表示旧的合作式 FIFO 语义：`submit` 只入队，
  `advance` 才在调用线程执行。`DeterministicAsyncPlanningExecutor` 仅为弃用兼容名，
  不创建后台线程。
- `SynchronousPlanningExecutor` 保持 `submit` 立即在调用线程计算的兼容语义。
- `ThreadedPlanningExecutor` 使用一个标准库 worker thread 严格按 FIFO 启动任务。
  worker 只产生不可变 completion；只有 session 调用 `advance`/poll 时才能改变状态、
  READY 队列、事件、generation、lineage 和统计。
- queued task 可在开始前真实取消且不会调用 backend。running task 只能发起合作式
  logical cancellation，不能强杀 Python thread；不支持 logical cancel 的 backend 会产生
  明确事件，晚到结果仍由 generation/lineage 门控丢弃。
- `shutdown` 幂等，关闭后拒绝 submit，可取消 pending task。`wait=False` 不代表 running
  worker 已停止；`wait=True` 使用有限 timeout，并要求调用方确保 backend 能退出。
- latency 分离为 queue、executor compute、backend-reported、authoritative validation 和
  end-to-end。executor 实测 compute 是控制面权威值；backend 自报值仅作诊断，不得覆盖。
  initialize/prewarm 继续独立统计，并增加 cancellation 与 stale-result 计数。
- 确定性并发测试使用 `threading.Event` 和有限 timeout，不以固定 sleep 推断调度状态；
  每个测试显式 shutdown worker。

## dev0 范围

- `MotionBoundaryState` 明确保存 `q`、`qd`、`qdd`、时间和
  `STOP_BOUNDARY` / `CONTINUOUS_BOUNDARY`。匹配使用显式 tolerance，并比较完整
  边界；相同 `q`、不同 `qd` 不可复用。
- `PlanEnvelope` 保存完整 expected start/end boundary，同时保留只读的旧 position
  属性。`PlanArtifactKind` 区分 geometric path 与 time-parameterized trajectory。
- geometric path 只能表达 stop boundary。当前几何 backend 仍为 stop-to-stop，本轮
  未增加时间参数化算法。
- plan lineage 记录成功完成集合、最后成功 plan 及 parent-to-child 关系。successor
  只有在准确 predecessor 成功后才能执行；failure、deviation、STOPPING 和
  invalidation 会级联失效 descendant。
- rolling horizon 计入 executing、ready、speculative、active planning 和 queued
  planning plan slots；同一 active/submitted request 不重复计数。horizon 2 表示 k 加
  最多一个 k+1，同一 predecessor 最多一个 live successor。
- backend capability、provenance、domain/operational failure taxonomy 保持 provider
  neutral。unsupported route 不计为 IK、collision 或物理不可行。
- backend `SUCCESS` 仅为 proposal。独立 `PlanValidator` 接口验证最新 snapshot、完整
  boundary、lineage 和模型 fingerprint 后才可进入 `READY`。兼容 adapter 可以代理
  v0.5.1 backend validation hook，但不能绕过 provider-neutral 门控。
- candidate/request/result/event 的嵌套 metadata 递归冻结，调用者后续修改原始
  dict、list 或 ndarray 不会改变控制平面记录。

## 明确不包含

- 不实现真实机器人 execution backend、控制器 runtime 或安全 PLC；这些留给
  `0.5.2.dev2` 及后续 integration 工作。
- 不实现或导入 VAMP、cuRobo、CoAd、CUDA、ROS 2 或新的仿真依赖。VAMP/cuRobo
  将来只能作为 `PlannerBackend` / `PlanValidator` adapter；CoAd 类方法只能作为必须
  重新验证的 FAST proposal source。
- FK、IK、机器人/环境碰撞几何、轨迹优化、时间参数化、grasp、depalletizing、
  conveyor 和 base optimization 继续归 feasibility/integration 功能线，本轮没有从
  `feat/v0.5-feasibility-core` 合并、cherry-pick 或复制实现。

## 验收边界

V3 原始 M-710iD/70 基线仍为完整几何 0/104、连续场景 0/129。测试不依赖这些任务
成功；bottom-alternative fixture 仍是当前唯一真实 M-710iD/70 integration witness。
rolling horizon 不等于无停顿连续运动。本版本不声明真实卸货成功率或
900 boxes/h，`production_throughput` 保持 `null`。

测试继续使用 synthetic scenes、deterministic unit scenes 及既有 bottom-alternative
fixture，不依赖第三方库、硬件或固定 sleep。

dev1 的 threaded fixture 使用真实后台 worker，但不连接硬件或第三方 planner。Python
thread 不保证纯 Python CPU planner 并行，不提供 hard deadline，也不能安全强杀 running
planner。`ExecutionMonitor` 仍不是机器人 execution backend。本版本只证明执行 k 时可在
后台计算 k+1，不证明 k/k+1 已实现非零速度无缝拼接，更不代表真实卸货吞吐。

VAMP/cuRobo/CoAd 仍只是未来 adapter：前两者只能经 provider-neutral
`PlannerBackend`/`PlanValidator` 接入，CoAd 类方法只能提供必须重新验证的 FAST proposal。
本版本未安装、导入或实现这些适配器。
