# V0.5 发布说明

发布日期：2026-09-07

## 发布定位

v0.5 的目标是先建立安全、确定、可测试的在线连续规划控制平面，使后续更强的
底层规划器可以通过 `PlannerBackend` 接入，而不需要重写在线状态机。

V3 最新基线中，原始 M-710iD/70 完整几何任务为 0/104，连续场景为 0/129。
因此本版本不把真实连续卸货成功率或 900 boxes/h 作为验收指标，也不宣称已经能
连续卸完整车厢。

## 新增能力

- `SceneRevision`：单调序号与确定性场景指纹。
- `PlanningRequest`、`PlanningResult`、`PlanEnvelope`：不可变、可审计的规划契约。
- `PlannerBackend`：可替换底层规划器，并显式暴露确定性随机种子。
- FAST、WARM、COLD 三级规划路径与确定性升级顺序。
- `ContinuousPlanningSession` 与 `ExecutionMonitor`。
- rolling horizon，以及执行 plan k 时预规划 k+1。
- speculative plan 与真实 scene 一致时快速复用，不一致时明确失效并重规划。
- scene revision 变化后的执行暂停、重新验证、失效和 stop acknowledgement。
- `ReplanReason` 与可审计 session event。
- 同步及协作式确定性异步执行抽象。
- planning latency 和 robot idle waiting-for-planner 统计。

## 失败语义

底层 backend 可以正常返回：

- `SUCCESS`
- `NO_IK`
- `GRASP_CONSTRAINT_FAILED`
- `INITIAL_CLEARANCE_FAILED`
- `COLLISION`
- `NOT_EVALUATED`

控制平面不会把失败包装成成功。每个目标/候选按 FAST、WARM、COLD 依次尝试，
之后切换候选和目标。所有已评估候选失败时进入明确的 `BLOCKED`；全部结果均为
`NOT_EVALUATED` 时进入 `WAITING_FOR_SCENE`；backend 异常进入 `RECOVERY`。

## 安全边界

- 可执行 plan 必须绑定并验证 scene revision。
- 执行中 scene 变化后，旧 plan 未经 backend 明确重新验证不能继续。
- speculative plan 只有在真实 scene 匹配或明确通过重新验证后才能提升为 READY。
- 本版本未修改 grasp、IK、depalletizing、conveyor 或 base optimization 内部算法。
- 当前时间参数化仍是保守 CPU、逐段静止到静止模型，不代表真实机器人生产节拍。
- 指标输出中的 `production_throughput` 固定为 `null`。

## 测试与证据

测试分为三层：

1. synthetic feasible scenes：验证状态机、scene revision、失效与 replan。
2. deterministic unit scenes：验证 FAST/WARM/COLD 顺序与 planning latency。
3. V3 bottom-alternative：校验 evidence zip SHA-256，并使用证据中的 57 个真实关节
   knot 作为当前 M-710iD/70 集成 fixture。

发布前默认测试结果：

```text
254 passed, 1 deselected
```

被排除项目沿用仓库默认 pytest marker 配置，不将 104 个原始任务成功作为测试前提。
