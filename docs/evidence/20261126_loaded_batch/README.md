# 2026-11-26 晚：带载前的五项问题与现场运行复查

来源：用户提出的五项问题，以及现场任务 1a5d6d89、ef4773e6、16425baa、a36db921、0aeed05e、cc2546c8、37188dbb、f96dd018。

## 已改并验证的

1. **规划耗时**：之前说“多出的时间花在找释放高度上”是误判。离线重放 18.4 s 中，12.9 s 是规划进程池冷启动（`native.resident_wait_ready`），目标搜索 2.9 s，14 次释放逆解合计 0.27 s。现场记录的规划耗时是 4.5–7 s，没有变慢。
2. **少数吸盘吸附**（`cup_fit.png`）：吸盘阵列约 180 × 130 mm，箱面约 133 × 109 mm。现行唯一位姿的两条规则（面中心、用下两排）正好让边列和上排压在面的边缘，能密封的只有 2、1、0 个。
   - 改动：`single_contact.in_face_shift=CUP_GRID`（代码默认，依据为用户决定“同一朝向加面内平移”）。朝向不变，阵列沿吸盘网格（吸盘中心及相邻两盘之间的中点）在面内平移；候选按预计密封个数从多到少、离原位从近到远排序；密封和接触检查不变。
   - 效果：9ec45e42、37188dbb、f96dd018、1a5d6d89、cc2546c8 最多可密封 3、2、4、4、4 个。
3. **三维几何变慢**：Wi-Fi 上行约 60 KB/s，SSH 发送队列积压约 260 KB；远程服务器推理 0.2 s，没有问题。
   - 改动：`detector.remote.image_encoding`，默认 `JPEG95`（质量 95，4:4:4 色度采样）；服务器同时接受 PNG 和 JPEG；所用编码写入推理记录。深度不上传。
   - 效果：一帧从 437 KB 降到 107 KB，检测从 9.2 s 降到 2.8 s；检测框坐标差在 1 像素以内，置信度差约 0.01，测出的箱体相同。
4. **释放点跟着起点走**（ef4773e6 找不到释放逆解；16425baa 起点 J6 −175°，接近段转 176°、返回段转 −169°）：
   - `release_pose.position_xy_m=[-0.073,-0.576]`、`start_height_m=0.4843`：固定为原来的释放点（9ec45e42 起点时的吸具末端位置）；
   - 释放朝向 = 目标接触朝向随 J1 转到释放点方位后，再向下翻腕；
   - 找到的高度按（位置，朝向）缓存。
5. **带载时恢复否决**：`loaded_return_collision=RECORD_ONLY` 只在空载演练中生效。带载配置 `single_carton.field_continuous_loaded_20261126.json`：关闭空载演练（吸附时机仍是“贴住后再吸”），去掉“只记录”，使用固定释放点。
6. **外拉余量**改为可配置（`detach_outward_clearance_m`），默认仍为 0.01 m，见下文。

## 试过但无效、已撤回的

- 外拉余量 0.10 m：外拉段本身出现 `SINGLE_CARTON_PAYLOAD_SUPPORT_PENETRATION`（沿倾斜的箱面法向拉 30 cm，箱底压进按测量倾斜的支撑面）。
- 带箱返回段 Pilz 不通过时改用 OMPL：每次都是 `NATIVE_SOLVER_BUDGET_EXHAUSTED`（5 s），只增加耗时。
- 搬运中间点（先不翻腕搬到释放点上方，再翻腕）：从脱离终点出发的第一段起点就被拒（`INVALID_START_CLEARANCE`），因为脱离终点仍贴着邻箱，而返回段没有接触许可。另外，搬运朝向朝底座外侧时，箱子会碰到 −Y 工作空间边界。

## 未解决

用带载配置在 6 条记录上走生产计划入口：1a5d6d89 26 s、ef4773e6 61 s、9ec45e42 88 s、cc2546c8 136 s（超过现场 90 s 时限）计划就绪；37188dbb、f96dd018 没有计划。大部分候选被拒，原因是带箱返回段扫到邻箱或补出的体积。
