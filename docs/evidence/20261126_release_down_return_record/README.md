# 2026-11-26 首次真机空载跑通后的四个问题

来源：现场任务 9ec45e42（单箱，完整跑通，物理验收 NOT_RUN）和 3ffe1c25（连续作业第 1 轮，带箱返回段停机），代码 d745ce1。

## 1. 脱垛不是直线，而是向上

- 五种脱离方式（直接外拉 OUTWARD、45° 斜拉、先抬后拉、少量抬升、竖直抬升到全高）的脱离段路径审计**全部通过**。
- 被放弃的原因都在**带箱返回段**：外拉、斜拉、先抬后拉三种，返回段的发送路径审计里，箱子和右侧邻箱（carton-1）相交；少量抬升那种，返回段规划时起点就已经贴着邻箱。返回段用 Pilz 关节插值，中间经过“带箱返回中间点”，从外拉终点出发时会把箱子扫向邻箱。规划器于是一路换到“竖直抬升到全高”。
- 用户决定：“保留直拉，带载返回段的碰撞只记录，不否决”，范围是“返回段所有碰撞”。
- 实现：`loaded_return_collision={mode: RECORD_ONLY, basis}`（`planner.loaded_return_policy`）。
  - 返回段的发送路径审计和带箱终点状态检查，发现碰撞时写入 `*-collision-recorded.json` 和段证据（`sent_path_collision=COLLISION_RECORDED_NOT_VETOED`），不再否决计划。
  - 其他各段、规划本身、审计本身都不变。
  - 代码默认关闭，只在现场配置 `single_carton.field_continuous_release_down_20261126.json` 里打开。
  - 这是现场前提：真正吸着箱子时，返回段记录到的碰撞会真实发生。

## 2. 接近时吸盘不平行于箱面，只有少数吸盘贴上

- **规划和执行是一致的**：吸具 +Z 轴和算出的箱面法向（取反）的夹角为 0.000°；接触时实测关节换算出的位姿，与计划的最大间隙 0.23 mm（3ffe1c25 为 0.18 mm）。所以“不平行”不是法向计算方式或执行的问题，而是算出来的法向本身与真实箱面有偏差。
- 五帧（J1 为 73.7° 和 78.3°）对比：
  - 两只上箱正面的偏航一直在 −6.4° 到 −8.7°；
  - 正面法向仰角在 −1.6° 到 −2.7°（略朝下），而下箱正面在 +0.2° 到 +0.9°；
  - 实测箱体竖轴相对 +Z 倾斜 2–6°。
- 背景：11-25 记录过标定文件与模型相机的朝向相差 82°，用户决定“就用现在的标定文件，先忽略”；相机下移、桅杆按新模型改装之后**没有重新标定**。
- 判断：最可能是相机外参的残余转角（几度级别），也可能是箱垛本身就转了约 7°。两者在数据里无法区分，需要现场核对：箱垛正面是否垂直于机器人底座 X 轴。
- **少数吸盘贴上**是按设计算出来的：箱面只有 0.109–0.133 m 宽，只有 2 个吸盘（part_012、part_018）的完整密封圈能落在箱面内并留出边距，其余吸盘按被动自闭处理。吸持能力评估为**不足**（抗剥离裕度 0.44–0.45，要求至少 1）。吸持检查目前按 11-24 的用户决定“只记录、不拦截”，所以真吸附时可能吸不住或中途脱落。

## 3. 复位到一半停住

- 3ffe1c25：带箱返回段发出第 2993 个点（共 4662 个）后，下一点没有在 5 ms 周期内按时发出，晚了超过 2 ms 的容许抖动，触发 `SEND_DEADLINE_MISSED`，安全停机（停机已确认，没有持箱）。之后的复位规划、执行都完成了，到达起点，最大偏差 0.08°。
- 近 12 段运动的发送抖动：p99 约 0.6 ms，最大 0.79 ms，没有一个超过 1 ms。这次是单次超过 2 ms 的卡顿。
- 发送循环在单独的子进程里，但用的是普通调度；本机 `ulimit -r` 为 0，普通用户不能使用 SCHED_FIFO/RR。
- 实现：发送线程启动时申请 SCHED_FIFO（优先级 20），申请不到就照常运行，实际拿到的调度类别写入控制器能力记录 `sender_scheduling`。抖动、发送间隔等监控阈值都不变。
- 开权限需要用户用 sudo 执行系统配置（见交付说明），这属于系统改动，由用户决定和执行。

## 4. 释放姿态改为吸具朝向 −Z、释放位置不变

- 用户决定：“释放的姿态要改为吸具朝向-Z，释放位置保持不变”；释放后“直接从释放点规划到下一箱的接近点”。
- 原释放点在离底座轴线 0.58 m、高 0.484 m 处，吸具朝下时够不着（原生 IK 和数值估算都无解）。用户决定：“水平位置不变，自动降高度”。
- 实现（`release_pose.py`，`release_pose={mode: TOOL_DOWN_SAME_POSITION, basis}`，仅用于四段式循环）：
  - 释放点的 X、Y 取起点时吸具末端的位置；
  - 吸具轴向用最小转动转到 −Z，不额外绕 Z 转；
  - 高度从原高度起每 2 cm 往下试，第一次有逆解后再往回细找 1 cm，不低于工作空间下边界；
  - 取原生 IK 解，并用 FK 核对（位置 ≤ 1 mm，轴向 ≤ 0.5°）。
- 带箱返回段的终点改为 `q_release`，在那里释放，这一轮也在那里结束（循环检查 `RETURN_NOT_Q_RELEASE` 和 FK 证据）。下一轮的冻结起点就是这个位姿，再求释放位姿时，吸具已经朝下，直接在原地释放。
- 连续作业：下一轮的起点改为与上一轮结束位姿比较（原来是与首轮起点比较），四段式原流程下两者相同。
- 9ec45e42 离线重放：高度降了 0.23 m（吸具末端从 0.484 m 降到 0.254 m），`q_release` 约为 [77.0, −42.2, −17.4, −30.4, 90.0, −12.0]°，FK 误差为 0；脱离方式改回 OUTWARD；返回段碰撞（箱子对 carton-1）已记录、未否决；规划 2.8 s。

## 补充修正（同日，现场任务 85ac057f、f263e028）

- 现象：6bc1b31 部署后，两次规划都在登记计划时被拒（`SENT_PATH_CHECK_MISSING`），没有发出运动。
- 原因：带箱返回段的审计结论改成了“碰撞已记录”（`COLLISION_RECORDED_NOT_VETOED`），但规划器登记前的检查和轨迹授权模块（`controlled/trajectory.Authority.register`）都只认“通过”。之前的离线重放走不到登记这一步，所以没有发现。
- 修正：`controlled/trajectory.sent_path_accepted` 只对带箱返回段（`return` / `transfer`）放行，而且证据里必须写明规则 `LOADED_RETURN_COLLISION_RECORDED_NOT_VETOED_2026_11_26` 和依据；其余各段仍必须“通过”。
- 验证：用生产计划入口（`replay --plan-cycle-entry`：搜索、绑定、逐段登记、完整计划、`Cycle.ready`）在 f263e028 上对比。旧代码复现 `SENT_PATH_CHECK_MISSING`；新代码 `PLAN_READY`，4 段都登记成功，入口到计划就绪 17.5 s。新增 1 项授权放行测试，相关测试 347 项通过。
